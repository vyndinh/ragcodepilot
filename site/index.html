A local semantic code search and generation CLI

Search your codebase using plain English, right from the terminal.

ragcodepilot indexes source repositories locally with Go AST function-level chunking, embeds code via Ollama (nomic-embed-text), indexes BM25 keywords, and executes server-side Reciprocal Rank Fusion (RRF) inside Qdrant — optionally generating answers with source citations via --answer.

    🧩 Follow one function through the system

    The same ChunkFile function moves from a local file to a cited answer. Source text is real; the abbreviated payload and answer below are teaching examples.

    1. 1. Read & chunk

      The walker selects internal/ingest/chunker.go. The Go parser retains the function and its doc comment, lines 20–28, as one named chunk.

      // ChunkFile reads a source file and splits it into chunks.
// For Go files, it uses go/parser to produce function-level chunks.
// For all other languages, it falls back to a line-based sliding window.
func ChunkFile(filePath, repoRoot, repo string, chunkSize, overlap int, cfg *config.Config) ([]model.CodeChunk, error) {
    if cfg.DetectLanguage(filePath) == "go" {
        return chunkGoFile(filePath, repoRoot, repo, chunkSize, overlap, cfg)
    }
    return chunkGeneric(filePath, repoRoot, repo, chunkSize, overlap, cfg)
}

    2. 2. Add context for embedding

      Prefix the code with this header. The enriched text is used for dense embeddings and sparse document vectors; the original code remains the stored payload.

      File: internal/ingest/chunker.go
Language: go
Function: ChunkFile

[the same source text from step 1]

    3. 3. Store one point in Qdrant

      The CLI calls Ollama over HTTP for a dense vector, builds BM25 document weights using corpus statistics, then upserts both over gRPC.

      collection: code_chunks
vectors: dense [768 floats], sparse {term IDs, BM25 weights}
payload: {repo, file_path, language: go, name: ChunkFile,
          chunk_type: function, start_line: 20, end_line: 28,
          content: original source, file_hash, index_version}

    4. 4. Retrieve the stored chunk

      Query: “where is ChunkFile defined”. Hybrid mode embeds it and tokenizes it into sparse terms with weight 1.0 each. Qdrant filters both candidate lists and fuses their positions with RRF.

      The saved baseline_v8 run returned this function at rank #1. This is a recorded result on this repository, not a guarantee for other corpora.

      Stop: a hypothetical 1,536-dimensional query vector does not match this 768-dimensional collection. ValidateCollectionVectorSize returns an error before vector lookup. Use the matching embedding model, or intentionally rebuild the index for the new model. No retrieval or answer is produced.

    5. 5. Print code, or request an answer

      Default: return ranked code chunks. With --answer: warm the local generator, select up to --answer-limit chunks (default 5), build the prompt, and call Ollama /api/chat.

      “ChunkFile is defined in internal/ingest/chunker.go. It dispatches Go files to the AST chunker and other files to the generic chunker. [1]”

    🔬 Technical Deep Dives

    ENGINEERING DECISIONS

    Explore the foundational algorithms and engineering decisions that power high-precision code retrieval.

    Go AST Function-Level Chunker

    internal/ingest/chunker_go.go
    STRUCTURALLY AWARE

    Parses Go with go/parser. Keeps function/method declarations and named types/interfaces together when they fit. Declarations longer than 80 lines use sliding-window splitting; syntax errors fall back to the generic chunker.

    // AST Chunker extracts complete logical units: // - Package name // - Docstring comments // - Method receiver (e.g., (c *Client)) // - Function name & signature // - Full function body from { to } // - Large declarations can still cross syntax boundaries when split.

    Generic Sliding Window

    internal/ingest/chunker.go
    GENERIC FALLBACK

    Used for languages without dedicated AST parsers (Python, TypeScript, Shell). Slices files into 40-line windows with a 5-line overlap, using regex heuristics to extract surrounding identifiers.

    // 40-line sliding window + 5-line overlap (DefaultChunkLines/DefaultChunkOverlap) // Regular expression fallback identifies: // - func / def / fn definitions // - Overlap retains some neighboring context // - It cannot guarantee intact syntax or a relevant search hit

    Raw Code Chunk

    Before Enrichment
    RAW TEXT

    Embedding raw code without context leads to false positives when functions use common verbs or variables like Search or Init.

    func (c *Client) EnsureCollection(ctx context.Context, name string, vectorSize uint64) error { // ... checks collection existence ... }

    Enriched Embedding Input

    internal/ingest/enrichment.go
    STRUCTURAL CONTEXT

    Prepending the file path, language, and chunk type/name gives the embedding input explicit context. Repository and signature fields are not added to this header; a signature may already appear in the raw code.

    Why Hybrid Search? Reciprocal Rank Fusion (RRF) with k=60

    Dense vector embeddings excel at semantic similarity (e.g. matching "how does chunking work?" with ChunkFile), but struggle with exact symbol navigation (e.g. "SearchWithTimings"). BM25 complements them with identifier and keyword matches. RRF fuses them without needing fragile score calibration:

    Score(chunk) = Σm ∈ {dense, sparse}   [ 1 / ( 60 + Positionm(chunk) ) ]
    DENSE COSINE

    Ollama 768d vector captures natural concepts, high-level intent, and synonyms.

    SPARSE BM25

    Split identifier tokens, preserved full identifiers, and additive stems support keyword matching.

    SERVER-SIDE RRF

    Lookup and fusion run inside Qdrant in one query RPC; the CLI still handles encoding and transport.

    Incremental Reindexing & SHA-256 Change Detection

    File hashes skip work only when the entire corpus is unchanged. BM25 IDF is corpus-wide, so if any file changes, every current file is re-chunked and re-embedded.

    1. SHA-256 HASHING

    Each file's SHA-256 is compared with Qdrant payloads. If hashes and index version all match, indexing is a no-op.

    2. INDEX VERSIONING

    Tokenizer or chunker changes bump index_version so unchanged files still refresh sparse/chunk shape.

    3. --watch (same pipeline)

    index --watch debounces fsnotify events and re-runs the full index pipeline — not a per-file embed-only daemon.

    🚀 Run it on your machine

    Install Go —, Git, Docker with Compose, and Ollama first. Start Docker and the Ollama app/service. Commands below run in your terminal, not in this website.

    1. 1. Get the source

      If you already have this repository, open its root directory and skip cloning.

      git clone https://github.com/thuyvy3110/ragcodepilot.git
cd ragcodepilot

    2. 2. Start services & download embeddings

      Qdrant runs in Docker; Ollama runs on the host. If Ollama is not already running, start ollama serve in a separate terminal. Downloads require internet access.

      docker compose up -d qdrant
ollama pull nomic-embed-text
go run ./cmd/ragcodepilot version

    3. 3. Index this repository

      Wait for indexing to finish before searching. This creates the default code_chunks collection using Go source files.

      go run ./cmd/ragcodepilot index --language go .

    4. 4. Retrieve code

      Hybrid search returns ranked source chunks, file paths, and line ranges. It does not need a generative model.

      go run ./cmd/ragcodepilot search "how does chunking work?"

    5. 5. Optional: generate an answer

      Download the additional model, then use --answer. The first call can take longer while the model loads. Inspect its source citations to judge the answer.

      ollama pull qwen2.5-coder:7b
go run ./cmd/ragcodepilot search --answer "how does chunking work?"
    Service errors or an empty search?
    • Ollama connection refused: start the Ollama app or ollama serve. Run ollama list to check downloaded models.
    • Qdrant connection refused: check docker compose ps and docker compose logs qdrant. The CLI uses port 6334.
    • Missing collection or no results: finish indexing first and use matching collection/language/repository filters.
    • Vector dimension mismatch: use the same embedding model for index and search, or deliberately rebuild for the new model.
